# Один процесс для дашборда и MCP

**Цель.** Один `mcp-huddle --http` обслуживает два прежних адреса: дашборд
`127.0.0.1:8014` и MCP `127.0.0.1:45111`. MCP — протокол и набор инструментов,
которые используют агенты. Оба адреса ведут в один ASGI app и один процесс.

## Что изменено

Команда `--mcp-port` добавляет второй loopback listener (сетевой порт только на
локальном компьютере) к существующему `--port`. Один экземпляр Uvicorn
обслуживает оба сокета одним приложением и одним жизненным циклом. Без
`--mcp-port` прежняя команда `--http --port 8014` сохраняет прежнее поведение.
Оба сокета связываются до сообщения о готовности; если второй порт занят,
первый закрывается, запуск завершается ошибкой. Оба порта используют ту же
проверку токена, что и один HTTP app.

Проверка изолированной MCP-сессии подтверждает `initialize`, затем
`tools/list` с выданным `Mcp-Session-Id` на том же app. Тест CLI проверяет, что
оба сокета передаются одному экземпляру Uvicorn. Он не запускает живые порты.

## Подготовка установки

Сначала используйте исходный checkout `/Users/kolotovalexander/Apps Projects/AgentSync/mcp/huddle`,
если именно он сейчас обслуживает launchd (менеджер фоновых служб macOS).
Временная ветка `/private/tmp/huddle-memory-http` нужна только для проверки;
не оставляйте launchd привязанным к этому временному пути. Если решено сначала
испытать ветку, укажите её как `--source`, сохраните отдельный кандидат plist,
а перед постоянной установкой заново создайте кандидат с основным checkout.

Сохраните точный путь действующего plist дашборда и его резервную копию. До
генерации плана проверьте `launchctl print-disabled gui/$(id -u)` и подтвердите,
что bridge override сейчас включён (bridge не находится в списке отключённых).
Если состояние иное или неясно, не используйте напечатанный план переключения.
Скрипт
ниже читает этот plist как шаблон и создаёт новый файл только по отсутствующему
пути. Он сохраняет label, лимиты, рабочую директорию, пользовательские
переменные и прочие launchd-настройки. Обновляются только `ProgramArguments` и
`PYTHONPATH`; прежний `PYTHONPATH` добавляется после пути выбранного исходника.
Живые launchd-службы скрипт не меняет.

```bash
python3 tools/plan_single_server.py \
  --template "/точный/путь/к/действующему-dashboard.plist" \
  --python "/точный/путь/к/python-из-текущего-окружения" \
  --source "/Users/kolotovalexander/Apps Projects/AgentSync/mcp/huddle" \
  --output "/private/tmp/huddle-dashboard-single-server.plist" \
  --backup "/private/tmp/huddle-dashboard-original.plist" \
  --bridge-plist "/точный/путь/к/действующему-bridge.plist" \
  --bridge-label "com.kolotovalexander.toolhive.agentsync-pilot-vmcp.bridge.agentsync-huddle-bridge" \
  --bridge-was-enabled
plutil -lint "/private/tmp/huddle-dashboard-single-server.plist"
```

Скрипт печатает точную последовательность переключения и отката с найденными
в plist label, путями, владельцем/правами plist и GUI UID. Он отказывается перезаписывать выходной файл,
резервную копию или любой из двух действующих plist. Команды печатаются для
проверки; скрипт их не запускает.

Перед применением сравните исходный и кандидат plist, включая
`EnvironmentVariables`, `WorkingDirectory`, `KeepAlive`, `ThrottleInterval`,
`StandardOutPath` и `StandardErrorPath`. Убедитесь, что кандидат запускает
`python -m mcp_huddle --http --port 8014 --mcp-port 45111`, а `PYTHONPATH`
указывает на выбранный checkout. Не удаляйте plist моста: он нужен для отката.

## План переключения и отката

Применение выполняется отдельно и требует согласованного окна: краткое
переключение прервёт подключения MCP. До переключения сохраните оба исходных
plist, их контрольные суммы, точные launchd labels, UID GUI-домена и вывод
`launchctl print`. Проверьте кандидат `plutil -lint` и запишите, какой checkout
будет активен.

1. Отключите override автозапуска bridge и выгрузите только job
   `com.kolotovalexander.toolhive.agentsync-pilot-vmcp.bridge.agentsync-huddle-bridge`,
   чтобы освободить `45111` и не запустить bridge снова при следующем входе.
2. Атомарно замените plist дашборда `com.kolotovalexander.huddle.dashboard`
   проверенным кандидатом и перезапустите только этот job.
3. Проверьте процесс, прослушивание обоих loopback портов, `/dashboard` на
   `8014`, затем MCP `initialize`, `tools/list` и комнатный read/write на
   `45111/mcp`. Убедитесь, что клиенты подключаются по прежнему адресу и нет
   второго процесса Huddle/моста.
4. Если любая проверка не прошла, выгрузите job дашборда, восстановите его
   сохранённый plist, включите override bridge и загрузите оба исходных job по сохранённым путям и
   проверьте прежние `8014` и `45111/mcp`.

Команды `launchctl bootout/bootstrap/kickstart` не запускаются этим изменением.
Перед применением подставьте реально найденные пути и GUI-домен, затем
проверьте состояние каждой службы. Не запускайте старую запись
`com.kolotov.mcp.huddle` из `mcp/manifest.yaml` параллельно.

## Сравнимый замер памяти

Снимайте до и после на одном Mac, под одной учётной записью и с одинаковым
состоянием Huddle. Используйте отдельную копию данных с одинаковыми комнатами
и сообщениями для обоих вариантов; не подключайте рабочие клиенты к копии. Не
запускайте агентов во время замера. Оставьте вкладку
дашборда одинаково открытой или одинаково закрытой и учитывайте браузер отдельно.
После запуска подождите одинаковое время, например 2 минуты, и сделайте пять
снимков с интервалом 10 секунд. Для каждого процесса запишите PID, команду, RSS
(резидентную память из `ps`) и physical footprint из `vmmap -summary`:

```bash
ps -o pid=,rss=,etime=,command= -p PID
vmmap -summary PID
```

Для каждого варианта запустите один и тот же запросный сценарий чтения и записи
на этой копии. До переключения включите в сумму dashboard HTTP, bridge proxy и
stdio-server child. После — единственный HTTP/MCP процесс. Сравнивайте медианы
пяти снимков при одинаковом сценарии; фиксируйте footprint и RSS отдельными
колонками, не складывайте их вместе. Также запишите наличие swap, число
комнат/сообщений, открытой вкладки и агентов. Общие страницы памяти macOS
означают, что разность сумм процессов — оценка, а не гарантированная экономия
физической памяти. Успешное объединение тоже не подтверждает цель 20 МБ.
