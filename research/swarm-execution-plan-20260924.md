# Huddle Swarm: план доведения функций

24 сентября 2026. Источник требований — [решения Александра](swarm-user-decisions-20260924.md). Исходный срез — [пилот и его ограничения](swarm-mode-plan-v3-20260923.md). Это рабочая очередь, а не заявление о готовности.

## Принцип исполнения

Каждый этап заканчивается пользовательским поведением, а не серией проверок внутренних деталей. Исполнители работают в отдельных Git worktree. Claude ведёт основные реализации; Antigravity и OpenCode получают независимые узкие задачи после проверки доступности их маршрутов. Координатор интегрирует изменения, сохраняет пользовательские решения и проводит один-два сквозных сценария на функцию. Старые тесты используются как регрессионный барьер, новые добавляются только для публичного поведения или значимого сбоя.

Основные реализации далее передавать Claude, когда CLI снова доступен. Текущий вызов Opus 5.5 завершился лимитом сессии; это ограничение внешнего Claude CLI, не текущего Codex. Для независимой узкой работы подходит дешёвая Luna. Antigravity в последней проверке вернул 503 Eligibility; передавать приватный код в OpenCode через запрещённый автоматической проверкой маршрут нельзя без отдельного разрешения. Не плодить новые тестовые комнаты для проверки каждого параметра.

## Обязательная проверка перед приёмкой

1. Четыре режима: один короткий сценарий показывает порядок приглашений, явное завершение раунда и право последнего слова в совете.
2. Файлы и права: одна маленькая Git-папка, два участника, общий каталог и вариант с дополнительными копиями; неподдерживаемый профиль и отсутствующий Guard отклоняются до запуска.
3. Отказ и замена: один отказ модели даёт не больше одной допустимой замены, прежний дочерний процесс остановлен, роль и сообщения сохраняются. Запрос разрешения не одобряется автоматически.
4. Дашборд: видно режим, роли, ход участников и итог; технический журнал не подменяет пользовательский статус.
5. Граница выпуска: проверка компиляции Python и синтаксиса JS, затем полный проектный набор только при выпуске или если адресные сценарии оставят существенный риск.

На работающем сервере `:8014` проверены HTTP 200 для `/dashboard`, `/api/rooms` и выбранной комнаты. В старой вкладке `127.0.0.1` динамические запросы браузера зависли, хотя терминальный запрос отвечал; новая фоновая вкладка с тем же адресом тоже не восстановилась. Через `http://localhost:8014` та же комната загрузила 96 комнат и четыре сообщения. Кнопка «Ответить» выбрала точное сообщение #2, переключила форму на комментарий и показала адресата; отправку не выполняли. Это подтверждает браузерную форму, но не полный цикл сохранения аннотации. Luna не нашла причины в коде загрузки. Нужен диагноз соединений `127.0.0.1`, если сбой повторится у пользователя; не подменять его предположительной правкой.

Следующий короткий маршрут: (1) закрепить модель и усилие в выбранных профилях и один раз подтвердить реальный ответ на фиксированный запрос; (2) один живой сценарий записи файла двумя поддержанными CLI в изолированном маленьком Git-проекте; (3) один искусственный отказ и успешная замена. После этих сценариев — доставка сообщений во время хода и ограниченные дочерние агенты. Полный набор тестов запускать на выпускном рубеже или при обнаруженном системном риске, не после каждого шага.
