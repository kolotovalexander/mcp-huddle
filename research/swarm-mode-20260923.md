## Вывод

Для Huddle первая полезная версия — **управляемая команда**: один ведущий отвечает перед пользователем, два исполнителя берут независимые части, отдельный проверяющий смотрит результат, ведущий собирает итог. Агенты могут общаться напрямую, но право изменять состав, договорённости и финальный результат остаётся у ведущего. Это соответствует #361 и уже существующим правам владельца комнаты. «Равноправный рой» из видео интересен как следующий эксперимент после пилотов: его автоматическое самораспределение и общая папка требуют отдельного учёта задач, защиты файлов и восстановления после сбоя.

## Что говорят первичные документы

1. [Claude Code Agent Teams](https://code.claude.com/docs/en/agent-teams): есть ведущий, общая очередь задач, прямые сообщения, самостоятельный захват задач; захват защищён блокировкой файла. Документация рекомендует независимые участки и раздельное владение файлами, предупреждает о затратах и конфликтах. Командная функция экспериментальная; не следует считать её автоматически готовым внутренним движком Huddle.
2. [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/multi_agent/): различает «агент как инструмент» (ведущий сохраняет управление и собирает ответ) и передачу управления специалисту. Эти схемы можно сочетать; для #361 подходит первая.
3. [Microsoft Agent Framework](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/): выделяет последовательное, параллельное выполнение, передачу управления, групповой чат и динамического координатора. Название swarm само по себе не определяет механизм.
4. [AutoGen Swarm](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/swarm.html): это передача хода между агентами по явному сообщению, с общей историей и условием остановки; она не означает одновременно работающих в одной папке исполнителей. [Условия завершения](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html) включают лимиты сообщений, времени, токенов и внешний Stop.

## Реальное основание в нынешнем Huddle

Проверено по `README.md`, `docs/TODO.md` и `src/mcp_huddle/server.py` текущего checkout:

- Комнаты, приглашения, `message_post(to, kind, reply_to, idempotency_key)`, чтение дельты и `room_status` уже есть. Адресный `kind=request` пробуждает агента; `reply_to` помогает связать ответ с запросом. Правило против циклов уже требует отвечать только на адресный запрос.
- `room_round_advance` открывает раунд только владельцем; `propose_resolution`/`resolution_vote` относятся к завершению обсуждения, а не к авторизации изменения файлов. `room_status` отражает живость, ожидаемые ответы и сбои пробуждения.
- Сохранённый claim пробуждения защищает от дублирования запуска одного агента. **Это не очередь задач с зависимостями, владельцами файлов и отдельными статусами проверки.** Слово «очередь» в README сейчас обозначает журнал адресных запросов.
- По умолчанию Claude/Codex запускаются в режиме только чтения; Antigravity не имеет гарантированного режима только чтения. Включение исполнителей с правом записи — отдельная явная настройка и обычные разрешения, а не свойство комнаты. Codex может возобновить нить; другие CLI работают одноразовыми процессами на каждом пробуждении. Неизвестный чужой wake lease нельзя просто очистить по PID.

## Режимы для продукта

| Режим | Взаимодействие | Где полезен | Приоритет |
| --- | --- | --- | --- |
| **Совет** | Несколько независимых мнений, спор ограничен раундами; ведущий подводит итог. Только чтение. | Архитектура, поиск причин, обзор изменений. | Уже близок к имеющемуся Huddle; пилот без нового права записи. |
| **Команда** | Ведущий назначает независимые задачи, исполнители напрямую уточняют контракты, проверяющий отдельно принимает/возвращает работу, ведущий выдаёт итог. | Функции с разными файлами/слоями, исследование с синтезом. | **Первая реализация по #361.** |
| **Эстафета** | Задача последовательно переходит от одного специалиста к другому с явным результатом и передачей контекста. | Зависимые шаги: исследовать → спроектировать → реализовать → проверить. | После базовой команды; не обещает ускорения за счёт параллельности. |
| **Равноправный рой** | Агенты сами заявляют участки из общей цели, договариваются, фиксируют решения и захватывают свободные задачи. | Когда границы заранее неизвестны, но части реально независимы. | Эксперимент после пилота; нужны атомарные claims, разрешение конфликтов и лимиты. |

Ось **разрешения** (только чтение / запись) и ось **рабочая копия** (отдельные worktree / общий checkout) должны выбираться отдельно от режима взаимодействия. Первые пилоты «Команды» безопаснее и понятнее в отдельных рабочих копиях, с интеграцией у ведущего. Общий checkout допустим лишь при непересекающемся владении файлами и наблюдаемой защите от перезаписи.

## Предлагаемый цикл режима «Команда»

1. **Вход.** Ведущий создаёт комнату с целью, критерием готовности, указанными агентами и ограничениями. Режим записи возможен только при уже полученном разрешении на конкретную работу. Не использовать `auto_spawn=True` для случайного выбора всего реестра.
2. **Координация.** Участники читают источник, пишут короткие карточки: участок, файлы, контракты между участками, риск, способ проверки. Ведущий утверждает непересекающееся распределение; пока оно не зафиксировано, запись закрыта.
3. **Исполнение.** Каждая карточка выдаётся одним адресным запросом с постоянным ID и ключом повторной доставки. Исполнитель пишет только свои файлы, сообщает блокеры адресно, возвращает ссылку на конкретный результат/коммит и проверку. Общие сообщения — только при изменении контракта.
4. **Проверка.** Назначенный независимый проверяющий сверяет критерий готовности, затронутые файлы и фактическое поведение. Он возвращает `accepted` либо конкретные замечания; исполнитель исправляет в ограниченном числе итераций. «Согласен» в чате не равен принятой работе.
5. **Сборка.** Ведущий интегрирует непересекающиеся результаты, проверяет общий результат, явно отмечает непроверенное и отвечает пользователю. Завершает комнату после сохранения результата и освобождения своих процессов.

Для будущего машинного учёта задачи минимальная карточка: `task_id`, `goal`, `acceptance`, `owner`, `reviewer`, `files`, `dependencies`, `status`, `attempt`, `request_message_id`, `result_message_id`, `idempotency_key`, `created_at`, `updated_at`. Переходы: `proposed → claimed → running → submitted → review → accepted` либо `changes_requested/failed/blocked`. Сначала проверить, можно ли представить пилот карточками в `message_post.meta` плюс агрегатор; при необходимости отдельный реестр должен иметь одного владельца записи и атомарные claims в хранилище, не нарушая порядок блокировок `bus.py`.

**Решения:** каждый участник может предложить; ведущий фиксирует версию контракта и область действия; исполнитель подтверждает, что увидел изменение перед следующим редактированием. Голосование может собирать мнения, но не заменяет права владельца и разрешения пользователя. Если возникает спор по файлу, оба прекращают запись в него до решения владельца.

**Остановка и восстановление:** лимит исполнителей, раундов согласования, исправлений, времени и/или стоимости; состояние `blocked` при ожидании человека; явная остановка владельцем; отсутствие новых содержательных сообщений не запускает ещё один раунд. При сбое не переиздавать задачу, пока не установлена судьба точного дочернего процесса и его wake claim; `unowned_lease` требует отдельного подтверждённого восстановления. Не выводить завершение только из тишины лога.

## Пилот и критерии решения о внедрении

Начать с двух-трёх реальных задач, у которых есть независимые части: одна исследовательская (режим «Совет»), одна кодовая с разными файлами («Команда»), одна с конфликтом контрактов как отрицательный случай. Сравнивать с одиночным исполнением одинаковой цели: время до принятого результата, расход токенов/денег, качество по заранее заданным критериям, число конфликтов/повторов, необходимость ручного вмешательства. Для кодовой задачи фиксировать рабочие копии, коммиты и проверки; отделять «агенты ответили» от «результат принят».

**Условие перехода к реализации:** на пилоте протокол даёт завершённую работу без повторной выдачи и потери изменений, проверяющий действительно находит/отклоняет дефекты, а стоимость и время оправданы. Если независимых участков нет, Huddle должен рекомендовать одиночный режим или эстафету. Числовой порог выигрыша согласовать после измерения базовой линии, а не брать из видео.

## Неясности перед проектированием API

1. Где должен жить реестр задач: в комнате Huddle или в постоянной GitHub-карточке? Рекомендация: оперативные задачи в комнате; GitHub Issue для долговременной цели и итога.
2. Кто может открыть запись и выбрать рабочую копию? Рекомендация: внешний ведущий, в границах текущего разрешения; агенты могут только предложить.
3. Как вести интеграцию разных worktree и отдельную проверку без автоматического merge? Рекомендация: первая версия оставляет сборку ведущему и не обещает автоматического слияния.
4. Как измерять стоимость разных моделей и учитывать Jev? Рекомендация: Jev даёт совет по выбору среди доступных слотов на обезличенном контексте; фактический запуск, разрешения и принятие результата делает Huddle/ведущий.
